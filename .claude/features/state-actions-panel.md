# Feature: State Actions Panel (onentry / onexit / Event Reactions)

## Purpose

Let a user edit a state's behavioral content — what happens on entry, what happens on exit, and how it reacts to internal events — through a structured form UI instead of hand-writing `<onentry>`/`<onexit>`/`<assign>` XML, with autocomplete over known variables/channels.

## User behavior

- Clicking a state (single click, not double) opens this panel scoped to that state, with up to three tabs: **onentry**, **onexit**, **event reactions**. The **onexit** tab is hidden whenever the state has zero onexit actions (`localExit.length === 0`) — onentry and event reactions are always shown. There is no in-panel affordance to add a *first* onexit action once hidden; a user who wants one has to switch to the Code tab and hand-write the `<onexit>` element, after which the tab reappears. If `activeTab` is `'onexit'` and `localExit` empties out — the last row is deleted, or a state switch lands on a state with no onexit actions while onexit was the active tab — the panel falls back to `'onentry'` rather than leaving `activeTab` pointed at a tab with no visible button.
- Each tab lists existing action rows; clicking a row opens it for inline editing; "+" opens a blank inline form to add a new one.
- Rows can be **drag-reordered** (grip handle), **copied** (copy icon; one shared clipboard holding either an `'action'` or `'reaction'` entry), and **pasted** into any tab, regardless of which tab the row was copied from. Cross-bucket pastes convert on the fly: a reaction pasted into onentry/onexit becomes an `assign` (location/expr kept, event/type dropped); an assign pasted into reactions gets the same defaults as the Add button (`event: 'vector'`, `type: 'internal'`).
- The panel also hosts the **"Initial State" checkbox** for simple/compound states — checking it can be blocked (disabled, with an explanatory tooltip) if doing so would merge two Initial State groups (see `initial-state-groups.md`); unchecking is always allowed. A marking that would nest a parallel state is **not** disabled: the click goes through, `ToggleInitialStateCommand` refuses it, and the canvas warning banner explains why (`decisions/scxml.md` #14).
- Typing a `this_`-prefixed identifier that doesn't match any known variable/channel in the Location or Expression field offers a highlighted "(new channel)" suggestion. The suggestion is only a hint: nothing is declared when it's picked. On Apply, the parent (`visual-diagram.tsx`) runs `syncThisChannels()` (`src/lib/utils/sync-this-channels.ts`) on the `this_` channels in the rows this Apply added or edited. Those rows are found by diffing against the state's previous action/reaction list (`changedItems`), because the panel always sends the whole list. It declares the missing ones and re-types generated ones from how assigns and conditions use them (`inferThisChannelChanges`, `datamodel-extractor.ts`). The scope is deliberate (user decision): an Apply never edits a channel outside what was applied. Types are still inferred from every use in the document, and problems with other channels are left to the Validation panel's warnings and Fix buttons. The same pass runs after a Transition panel condition Apply, so `this_number == 2` declares `this_number` as `0.0`, and a `this_x` first created as a bool is re-typed once the condition compares it to a number. Other variables' declared types count too (a `conf_` field's `confType`, else its initial-value literal), so `this_v = conf_enabled` with `conf_enabled="true"` makes `this_v` a bool; the sync repeats (up to 5 rounds) so chains like `this_c = this_b` settle as well, as long as every link is in the applied scope.
- **Autosave on leave** (client request, 2026-11-19: "I don't want to click Apply"). Leaving an open inline form saves it (`leaveForm`): clicking anywhere in the panel outside the form (another row, "+", a tab), switching tab, selecting another state, closing the panel, or the panel being hidden by another one. Only **Discard** and **Esc** throw an edit away. Apply stays as an optional button and, being greyed out, still shows when the form is incomplete. A row opened and left unchanged is closed without a save, toast or undo entry. An incomplete form is dropped with an "Incomplete action not saved." warning (silently if it's a new form with nothing typed). A reaction that `validateReactions` blocks is dropped with its reason plus "The reaction was not saved." On leave the form is never kept open, unlike an explicit Apply/Enter, because the user is moving on. Saving on every keystroke was rejected: each save is a full command, so it would declare half-typed `this_` channels, add one undo entry per keystroke, and re-render the document with half-written expressions.

## UI behavior

- The onentry/onexit tabs never show the `send`/`cancel` row pair generated by an "after X" time transition (`isTimerGeneratedActionString` in `time-transition.ts`, matched on the row's event/sendid following the `_t_N_timeEvent_N` pattern) — these are edited exclusively via the Transition panel's "after X" field. `visual-diagram.tsx` filters them out before constructing the panel's props, recording each hidden action alongside its original index in the source array (`hiddenEntryActions`/`hiddenExitActions: Array<{ index, action }>`). Applying an edit (`onApply`, `onNewChannel`) merges them back into the edited list via `mergeHiddenActions()` (`time-transition.ts`), which splices each one back in at its original index (clamped to the edited list's length) rather than appending at the end — this matters because onentry/onexit actions execute in document order, so a naive append could reorder an interleaved `send`/`cancel` relative to a `delayexpr` or `assign` action, silently changing what value the delay expression reads. Same filtering hides them from the state node's `entry:N`/`exit:N` canvas indicator (`scxml-state-node.tsx`). The code editor (Monaco) is unaffected — the elements are still written to the document.
- Only assign-type action rows are copyable (send/cancel rows have no copy button) — `handleCopyRow` returns early for non-`'assign'` rows.
- The assign target field is labelled **Channel** in the UI (user request, 2026-11-18); in code and SCXML it is still `location` (`formLocation`, `<assign location>`), and its placeholder still reads "variable or channel".
- **Keyboard flow Location → Expression → Apply** (user feedback, 2026-11-18: cut the click between the two fields). Accepting a Location suggestion (Tab/Enter/mouse) or pressing Enter in Location with no dropdown open moves the caret to the end of the Expression field (`focusExpression`).
- **Enter saves** (user feedback, 2026-11-19: no need to click Apply). Enter saves from any field once the form is complete (`isFormComplete`). In Location, Enter on a half-filled form moves to Expression instead. With the suggestion list open, Tab always just accepts and moves on, while Enter accepts and saves if the form is then complete. Mouse picks never save. With nothing highlighted, Tab/Enter pick an exact match for the typed text before the first item (`pickSuggestion`), so Enter on an unchanged row being edited keeps its value. `handleApply` itself refuses an incomplete form, so Enter in Event can no longer save a half-filled reaction. Shift+Enter in Expression adds a line. The form says so in the UI: an "Enter to save · Esc to discard" hint left of the buttons, plus "Apply (Enter)" / "Discard (Esc)" tooltips (`FormActions`'s opt-in `showKeyHints` prop; other panels using `FormActions` don't pass it). A single merged `target = expression` field was considered and rejected: it would need `=` vs `==` parsing and position-dependent autocomplete, and users would lose the field labels.
- The Expression field's autocomplete dropdown live-previews the highlighted suggestion spliced into the text as you arrow through it, without committing until Tab/Enter. **Caret pitfall** (bug, 2026-11-19, same fix in the Transition panel): writing the preview into the controlled textarea makes the browser jump the caret to the end, and that jump arrives through `onSelect` as if the user had moved it. A `useLayoutEffect` puts the caret back (after the previewed token, else at `exprCursorPos`), and `onSelect` is ignored while a preview is showing. Arrow Left/Right, Home/End or a click in the text cancel the preview, and suggestion rows `preventDefault` on mousedown so the textarea keeps focus.
- The Expression dropdown is **docked under the textarea at its full width**, like the Location dropdown, not floated at the caret (user feedback, 2026-11-19: the caret-anchored 200px box covered the text being written and clipped long names behind a horizontal scrollbar). Long names truncate with a `title` tooltip.
- **Suggestions are triggered by letters only** (user feedback, 2026-11-19; shared with the Transition panel via `getExpressionSuggestions`). An operand slot (`x == |`) shows nothing until a letter/underscore is typed, so numbers (`a = 2`) never pop the name list; operators are offered after an identifier + space, never after a numeric literal.
- Reaction rows show event name + type badge (`internal`/`external`) + `location = expr`, left-aligned (`align='start'`) since reactions can wrap to two lines; regular action rows are vertically centered.

## Internal architecture

- Actions are round-tripped as **pipe-delimited encoded strings** at the Command boundary (`"assign|location|expr"`, `"send|event|delayType|delayValue"`, `"cancel|sendid"`) — the panel's internal `ActionRow` union is richer/typed, but `toStrings()` flattens it to this string format before calling `onApply(entryActions: string[], exitActions: string[])`.
- Rows have **no persistent identity in the SCXML source** (they're plain tuples/attributes, not elements with ids) — the panel attaches a client-only `_rowId` (via `withRowIds`) specifically so React/dnd-kit can track a row's identity across a reorder without recycling identity by array index (index-as-id previously caused the dragged row to visually snap back before jumping — see the file's own comment).
- Two **independent autocomplete engines** run in this one panel: the Location field (single-identifier suggestions, `Suggestion` type) and the Expression field (multi-token expression suggestions via `getExpressionSuggestions`/`applyExpressionSuggestion` from `expression-autocomplete.ts`) — they have separate open/active-index/blur-timer state because their token models differ.
- Applying any change immediately calls `onApply`/`onApplyReactions` (parent-supplied), which in `visual-diagram.tsx` routes to `UpdateActionsCommand` (onentry/onexit) or `UpdateInternalEventsCommand` (reactions) — **not deferred to a panel-level "Save" button**; every row add/edit/delete/reorder/paste is its own immediate commit (each becomes its own history entry via the `'property'`/`'structure'` changeType).

## SCXML behavior

- onentry/onexit tab writes/reads `<onentry>`/`<onexit>` children containing `<assign>`/`<send>`/`<cancel>`/etc. — `UpdateActionsCommand` wipes **all** existing `<onentry>`/`<onexit>` elements (there can be more than one) and writes exactly one new element per type if any actions remain.
- The "event reactions" tab manages **targetless** `type="internal"|"external"` transitions with `<assign>` children — see `.claude/project/terminology.md` "Internal event reaction". `UpdateInternalEventsCommand` groups actions **by event name** so multiple rows for the same event collapse into one `<transition event="X">` with multiple `<assign>` children, and inserts new reaction transitions before the first pre-existing targeted transition to preserve ordering conventions. Because of that ordering, a `done.state.<id>` reaction would silently shadow an existing `done.state.<id>` edge, so adding/editing or pasting a reaction first runs the optional `validateReactions` prop (`checkReactionsDoneStateConflict` in `transition-slot-rules.ts`, wired in `visual-diagram.tsx`): a blocked list isn't saved, the form stays open, and the reason is shown as a `warning` toast. Delete and drag-reorder skip the check (they can't add an event), so a conflict that already exists in hand-written SCXML never traps the user.

## Validation rules

None enforced *within* this panel beyond basic required-field disabling (`isApplyDisabled`) — full SCXML validation (unreachable states, slot conflicts, etc.) runs independently against whatever content results. The Initial-State and Final-State checkboxes are the exceptions: Initial proactively consults `initial-group-utils.ts` (`canMarkInitial`, passed down from the parent), and Final consults `checkCanMarkFinal` in `scxml-manipulation-utils.ts` (`canMarkFinal` + `finalBlockedReason` as the tooltip, recomputed from the live document while the panel is open) to block a would-be-invalid mark before the user can even attempt it. Final states open this panel too (onentry/onexit only, checked Final State checkbox, no Initial checkbox) — see `state-editing.md`.

## Known limitations

- No bulk/multi-row selection within the panel — copy/paste/reorder/delete all operate on one row at a time.
- Send/cancel action rows cannot be copied (only assign rows) — likely intentional (a copied `send`/`cancel` referencing a specific event/sendid is less obviously reusable) but not explicitly documented as such anywhere; verify before assuming it's a bug to fix.

## Important edge cases

- Switching the active tab (`onentry`/`onexit`/`reactions`) autosaves the open form (`leaveForm`), then resets it.
- Switching to a **different state** (`stateId` change) or the panel closing/hiding (`isVisible` change; the panel stays mounted while hidden) autosaves the open form to the state that *was* being edited, then resets `localEntry`/`localExit`/`localReactions` from the current props and resets the form. This relies on `leaveFormRef` still holding the previous render's `leaveForm` when the `[stateId, isVisible]` effect runs: the parent (`visual-diagram.tsx`) passes inline `onApply`/`onApplyReactions` closures bound to the `selectedStateForActions` of that render.
- The "new channel" suggestion only appears when the combined variable+channel suggestion list is otherwise **empty** and the typed text starts with `this_` — typing `this_` when it happens to partially match an existing channel/variable name will show that match instead of the new-channel option.

## Things that must NOT be changed

- Keep the effect that refreshes `leaveFormRef` declared **after** the `[stateId, isVisible]` reset effect. Effects run in declaration order, so swapping them makes autosave on a state switch use the *new* state's `onApply` and write the old form into the wrong state. Likewise, the parent must keep binding `onApply`/`onApplyReactions` to the state of the render they came from (closure), not read the selected state from a ref or store at call time.

- Do not switch row identity back to array index for drag-reordering — the `_rowId` (uuid) approach exists specifically to fix a visual snap-back bug with dnd-kit; this is documented in the file's own comment, not incidental.
- Do not change the pipe-delimited action string encoding (`"assign|location|expr"` etc.) without updating both `toStrings()` in this panel and the corresponding parser in `UpdateActionsCommand`/`extractActionsFromElement` — they must stay in sync.
- Do not merge timer-generated hidden actions back with a simple append (`[...edited, ...hidden]`) — always go through `mergeHiddenActions()`. onentry/onexit actions execute in document order, so appending at the end (rather than splicing back at the original index) can reorder an interleaved `send`/`cancel` relative to surrounding `assign`/`send` rows and silently change what value a `delayexpr` reads. See `decisions/editing.md` #9.
