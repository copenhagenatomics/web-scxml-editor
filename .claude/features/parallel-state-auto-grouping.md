# Feature: Automatic "Parallel State" Grouping of Multiple Initial-State Work Trees

## Purpose

Give multiple, mutually-disconnected Initial-State work trees (see `initial-state-groups.md`) real SCXML `<parallel>` semantics instead of leaving them as merely-adjacent siblings — live, on the actual document, not as a display-only or export-only transform. Originated from the same product requirement as `initial-state-groups.md` (`docs/parallel-states-requirement.md`), specifically its "Support for N-Parallel Machines" phase; reintroduces `<parallel>`/region structure previously implemented and reverted (commit `801145d`, reverted in `bf0ab49`) but scoped narrowly this time to only this automatic-grouping trigger, not a general manual "convert to parallel" feature.

## User behavior

- The moment a container (the `<scxml>` root, or any compound `<state>`) has **2 or more** distinct Initial-marked work trees among its direct children, the editor silently restructures the document: the trees become regions of a real `<parallel>` element, with no user action beyond having created the second group.
- The diagram shows **no separate box or label** for the `<parallel>` state itself — its member states render exactly as flattened siblings, at the same level as if they weren't wrapped at all (drill-down still works normally on any member that's itself compound).
- The only visible cue that a group exists is a full-height, dashed vertical **divider line** between horizontally-adjacent regions (violet, `rgba(124, 58, 237, 0.5)`) — one line per gap, not a box around each region.
- The whole group can be **dragged as one unit** by grabbing any empty space within its bounding area (cursor: grab) — every member state moves together, preserving their relative layout.
- Connecting two states that would **cross from one region into a sibling region** of the same `<parallel>` is blocked live while dragging a new connection, with the same dismissible-banner UX as the Initial-State-group conflict check.
- If a work tree later shrinks back to fewer than 2 groups (e.g. a member is deleted, or two groups get connected into one — see `initial-state-groups.md`), the `<parallel>` wrapper is automatically unwrapped back to flat siblings.

## Internal architecture

- **Marker attributes**: synthetic elements are tagged `viz:auto-parallel="true"` (on the `<parallel>`) and `viz:auto-region="true"` (on a region `<state>` wrapper needed for a multi-member work tree) — see `src/lib/utils/parallel-group-markers.ts` (`AUTO_PARALLEL_MARKER`/`AUTO_REGION_MARKER`). This is the **only** signal distinguishing auto-generated structure from a hand-authored `<parallel>` a user typed or pasted directly — those are never touched by any of this feature's logic (normalization, flattening, wrapper-node synthesis all bail out immediately for an unmarked `<parallel>`).
- A work tree with a **single member** becomes a bare region (that member's own `<state>` used directly, no synthetic region wrapper — `<parallel>`'s children must each be exactly one region, so a lone state can just *be* its region). A work tree with **2+ members** (connected via sibling transitions, same union-find analysis as `initial-state-groups.md`) gets wrapped in a synthetic `viz:auto-region="true"` `<state>`.
- **Core algorithm** — `src/lib/utils/parallel-group-normalization.ts`:
  - `normalizeParallelGroups(scxmlDoc)` — recursively walks every container bottom-up, re-deriving each one's wrap/unwrap decision fresh from its current flattened children (`buildLogicalView`) on every call; nothing is persisted beyond the document itself, same "recompute from scratch" style as `initial-group-utils.ts`.
  - `applyWrapDecision` — the actual wrap/unwrap for one container; a no-op (doesn't even canonicalize array-vs-object child shape) when there are fewer than 2 groups AND the container isn't already auto-wrapped, so hand-authored content this feature has no opinion about is never rewritten.
  - `collectAutoParallelGroups(scxmlDoc)` — read-only query used by the diagram/layout layer: every `viz:auto-parallel` group currently in the document, with each region's flattened member ids (`AutoParallelGroupInfo`).
  - `hasAnyChildren(container)` — counts members hidden inside an auto-wrap (plain `!container.state` under-counts once wrapping is in play); guards "auto-mark the first child Initial" conveniences elsewhere so they only fire for a genuinely empty container.
- **Single choke point**: `normalizeContent()` in `src/stores/editor-store.ts` calls `normalizeParallelGroups` and is invoked from both `setContent` and `setFileInfo` — every mutation path (Commands, diagram edits, file load) goes through the store and gets normalized there. The Monaco/XML-editor typing path (`src/app/page.tsx`'s `handleContentChange`) deliberately does **not** normalize on every keystroke — it calls `setContent(newContent, { immediate: false })` for live preview/validation, then commits the normalized version via `setContent(..., { immediate: true })` once typing pauses, piggybacking on the same 500ms debounce boundary `trackTextEdit` already uses for history entries.
- **Diagram flattening** happens at the registry layer: `collectEffectiveStateChildren` (`src/lib/converters/converter-modules/state-registry.ts`) folds an auto-wrapped `<parallel>` child's members (unwrapping one further level of `viz:auto-region` if present) directly into its container's effective child list — so the wrapper is **never a real navigable node**; `registerAllStates` skips an auto-wrapped `<parallel>` entirely (a hand-authored one still registers/recurses normally), and `useHierarchyNavigation` needed no changes at all.
- **Layout pipeline order** (`src/lib/converters/scxml-to-xstate.ts`, inside `convertToReactFlow`), all three steps run in this specific sequence and each depends on the one before:
  1. `applyDefaultELKLayout` positions every node normally (flat per-level layout, `viz:xywh` priority — see `decisions/visual-diagram.md` #4/#5).
  2. `separateParallelRegions` (`converter-modules/layout-positioning.ts`) pulls each group's regions into non-overlapping horizontal bands — ELK's flat per-level layout has no notion of "region," so a region's members can otherwise end up interleaved with or fully sandwiched inside a sibling region's x-span, making a single straight divider line impossible. Runs **immediately** after ELK layout and before anything else reads/persists positions (edge-handle selection, `viz:xywh` write-back, wrapper-node synthesis) — the pure math lives in `src/lib/layout/parallel-group-bbox.ts`'s `computeRegionSeparationTranslations`.
  3. `markParallelGroupMembers` flags every separated member's node data with `isParallelGroupMember: true`. This flag is read back downstream by `resolveEnhancedNodePosition()` (`src/lib/utils/resolve-enhanced-node-position.ts`): normally a node's saved `viz:xywh` takes priority over the converter's computed position (so manual placement survives re-render), but for a parallel-group member that would silently **undo** step 2's separation the moment the member's old, pre-separation `viz:xywh` got re-applied — this was an actual regression ("Parallel State regions stopped moving together with their divider line") before the flag was introduced. For a flagged member, the converter's own (already-separated) position is always authoritative.
  4. `computeParallelGroupWrapperNodes` (`converter-modules/layout-positioning.ts`) synthesizes one invisible "Parallel State" wrapper `ReactFlow` node per group, sized/positioned from the union bounding box of its now-separated members (`computeParallelGroupBBoxes`, same `parallel-group-bbox.ts` module). Its `data` carries `memberIds` (flat, for group-drag translation), `regions` (`{memberIds}[]`, for live divider recomputation — see below), and `dividerLines` (the divider x-positions **as of this parse**, since superseded — see Known limitations). Inserted **first** via `unshift`, not appended — with every node tied at `zIndex: 0`, browsers paint in DOM-array order, so this guarantees the wrapper paints *below* every real member node despite the wrapper's own `pointer-events: auto` drag zone spanning its whole bounding box; a click that actually lands on a member still reaches the member first.
- **Wrapper node** (`src/components/diagram/nodes/parallel-group-wrapper-node.tsx`, `ParallelGroupWrapperNode`, registered as ReactFlow type `scxmlParallelGroupWrapper`) renders **no visible content at all** — no border, background, or label, matching the "no separate box for the parallel state" UI requirement. Its whole area carries the `.parallel-group-drag-handle` class (the node's configured `dragHandle`) so the group can be grabbed from any empty space within its bounds.
- **Group drag**: since there's no real ReactFlow parent-child relationship between the wrapper and its members (this app never uses native nesting — same reason `collectEffectiveStateChildren` flattens at the registry layer), dragging the wrapper does not natively move its members. `expandWrapperPositionChanges` (`src/lib/layout/parallel-group-drag.ts`) expands one ReactFlow position-change event on the wrapper into one additional position-change per member (translated by the same delta), so `visual-diagram.tsx`'s existing `onNodesChange` pipeline moves — and, on drag-stop, persists — every member alongside the box. `handleNodeDragStart` tracks the member ids (not the wrapper's own synthetic id) for drop-target/reparent detection, since the wrapper itself is never a valid drag-to-nest source (it has no SCXML element of its own to reparent) and its own huge bounding box must not spuriously register as a drop target.
- **Region divider overlay** (`src/components/diagram/parallel/parallel-region-divider-overlay.tsx`, `ParallelRegionDividerOverlay`) is a viewport-synced sibling to `<ReactFlow>`, not embedded in any one node — each line spans the **entire visible canvas top-to-bottom**, independent of any group's own bounding box, so panning around a large group never leaves a boxed-in leftover working area. Only the horizontal position moves/scales with pan/zoom (`useViewport()` + `computeDividerScreenX`); `pointer-events: none` throughout so it never intercepts clicks. `visual-diagram.tsx` pools `dividerXs` across **every** currently-visible wrapper node (`parallelDividerXs`), not per-group, since the overlay is one shared layer for the whole canvas.
  - **Divider x-positions are recomputed live**, every render, from the current `nodes` array's live positions (`computeLiveParallelDividerXs`, `src/lib/layout/parallel-group-bbox.ts`) — **not** read off the wrapper node's own `data.dividerLines` snapshot. That snapshot is only as fresh as the last full SCXML re-parse, and a member's on-screen position changes live during a drag (or after a re-parse whose result briefly races a position-update lock — see the drag/connect race note below) well before any re-parse lands; reading the stale snapshot directly produced a real, reported bug where the divider only caught up once some unrelated event (e.g. clicking empty canvas) happened to resync `nodes`. `computeLiveParallelDividerXs` needs each wrapper's `data.regions` (not just the flat `data.memberIds`) to redo the same per-region union-rect/midpoint math `computeParallelGroupBBoxes` does, using each region member's *current* live position/dimensions instead of the positions captured at parse time.

## SCXML behavior

- The synthesized `<parallel>`/region structure is real, standards-conformant SCXML — a file with this document's `viz:auto-parallel`/`viz:auto-region` markers stripped (e.g. via "Clean SCXML" export) is still entirely valid, spec-compliant `<parallel>` usage; the markers exist purely so *this editor* can tell its own synthetic structure apart from something the user wrote by hand, not because the structure would otherwise be non-conformant.
- `wouldCrossParallelRegions` enforces W3C SCXML §3.4's rule that no transition may cross from one region of a `<parallel>` into a sibling region (LCCA-derived — see `git show 801145d:docs/parallel-states-scxml-spec.md` §1.4 for the original derivation notes from the reverted prior implementation). This applies identically to a hand-authored `<parallel>` and an auto-wrapped one, since it walks the live ancestor chain rather than checking for the marker.

## Validation rules

- **Live only, at connect-time** — `wouldCrossParallelRegions` is checked in both `onConnect` and `isValidConnection` in `visual-diagram.tsx` (the same dual-enforcement pattern `initial-state-groups.md` uses for group-merge conflicts), blocking the connection outright before it's created.
- **No static validator counterpart exists yet** — unlike `initial-state-groups.md`'s `wouldMergeDistinctGroups`, which is also re-checked by `initial-group-validator.ts` against the whole document (catching violations introduced by hand-edited/pasted XML that never went through the live UI), there is no equivalent static pass for cross-region transitions. A `.scxml` file hand-edited or pasted with a transition crossing regions of a `<parallel>` (auto-wrapped or hand-authored) will **not** be flagged by the validation pipeline — only the live drag gesture is guarded. See Known limitations.

## Known limitations

- **No static validator for cross-region transitions.** A hand-edited or pasted `.scxml` file can contain a transition crossing `<parallel>` regions with no live-drag gesture involved, and the current validation pipeline will not flag it — only `onConnect`/`isValidConnection` guard the live authoring gesture. (Cross-reference: `.claude/index.md`'s "Known issues" list.)
- **A member's `viz:xywh` intentionally does not round-trip through separation.** Once `separateParallelRegions` moves a member to keep its region non-overlapping, that new x is what gets persisted — there's no way to distinguish "the user manually dragged this to overlap another region" from "ELK's flat layout happened to place it there before separation," so a manual placement that lands inside another region's span is silently pulled back out on the next re-parse, same as any other separation. This is the intended behavior (see Design decisions), documented here as a limitation because it means the group's members are not fully free-form-positionable the way an ordinary state is.
- **`resolveEnhancedNodePosition`'s `isParallelGroupMember` override is coarse-grained** — it disables `viz:xywh` priority for **all** flagged members, not just the specific axis/case the original regression was about; a future change that needs a group member's saved position to win over the converter's computed one for some other reason would need to special-case around this flag rather than simply relying on the normal `viz:xywh`-wins rule.

## Important edge cases

- **A work tree shrinking back below 2 groups auto-unwraps** — `applyWrapDecision`'s `groups.size >= 2` / `else` branches are symmetric; there's no one-way "once parallel, always parallel" ratchet. A user deleting states or connecting two previously-separate Initial-State groups (see `initial-state-groups.md`) can silently turn a `<parallel>`-wrapped container back into flat siblings with `@_initial` pointing at the sole remaining root.
- **A single-member work tree gets no synthetic region wrapper** — its own `<state>` element is used directly as the `<parallel>`'s region child. `isAutoRegion()` returning false for that element is exactly how `collectAutoParallelGroups`/`collectEffectiveStateChildren` know to treat its single id as a one-member region rather than looking for further nested `.state` children.
- **A region can independently contain its own nested 2+-group situation** — `normalizeContainer` recurses into each region (auto-wrapped or hand-authored) exactly like any other container, so a `<parallel>` region can itself later grow a second Initial-marked work tree among *its* children and get auto-wrapped into a nested `<parallel>`, one level deeper.
- **The divider-recompute race**: both `onConnect`'s and the drag-stop position-commit's SCXML update briefly hold `isUpdatingPositionRef` true (to stop the main resync effect from clobbering an in-flight gesture) around their own async re-parse. If that re-parse's result lands *inside* that window, the resync effect's own dependency-triggered re-run finds the gate still shut and silently drops the fresh result — with nothing to naturally retry it, since nothing else changes those specific dependencies afterward. `applyLatestEnhancedNodesRef`/`applyLatestEnhancedNodes` in `visual-diagram.tsx` exists specifically to close this race: both call sites invoke it once they clear the gate, as a safety-net retry (a no-op if the parse hadn't landed yet, since the natural dependency-driven effect handles that case correctly once the gate reopens).

## Things that must NOT be changed

- Do not read a wrapper node's `data.dividerLines` directly for anything that needs to be accurate **during** a drag or immediately after a connect/reparent — it is a parse-time snapshot, not a live value. Use `computeLiveParallelDividerXs` (or extend it) instead; this is the exact bug class the "divider-recompute race" edge case above describes.
- Do not add a second, ad hoc cross-region-transition check anywhere new — always call `wouldCrossParallelRegions`, mirroring the "shared utility, never duplicated rules" principle `initial-state-groups.md` and `.claude/project/coding-rules.md` §3 already establish for the sibling `wouldMergeDistinctGroups` check.
- Do not give the `ParallelGroupWrapperNode` any visible border/background/label — that it renders nothing is an explicit requirement of this feature (distinct from the reverted `801145d` implementation, which did show a labeled parallel-state box), not an oversight to "fix."
- Do not treat a hand-authored `<parallel>` (no `viz:auto-parallel` marker) as fair game for any of this feature's logic — normalization, flattening, and wrapper-node synthesis all gate on the marker specifically so hand-authored `<parallel>` content is left completely untouched.

## Previous design decisions

- `docs/parallel-states-requirement.md` — the original informal product requirement (same document `initial-state-groups.md` cites), whose "Support for N-Parallel Machines" phase this feature implements.
- Commit `801145d` — an earlier `<parallel>`/region implementation that **showed** the parallel state as its own labeled box; reverted in `bf0ab49`. This feature reintroduces the underlying `<parallel>`/region document semantics but deliberately keeps the diagram flattened/non-drillable with no visible wrapper box — a narrower design than what was reverted.
- A **separate, unrelated sibling branch `new-parrallel-state-design`** (not merged as of this writing) adds a different, *manual* region-drilldown editing view for existing `<parallel>` states (side-by-side columns, add-state/add-region controls). The two features are designed to coexist via the `viz:auto-parallel` marker (auto-wrapped groups stay flattened/non-drillable per this doc; a hand-authored `<parallel>` would get that branch's drilldown view if it's ever merged) but are **not** integrated together as of this writing — verify whether that branch has since been merged before assuming its region-view code is still absent.
